Stage 5: Metadata Subagent

Stage 1 of Cascading Retrieval Universal (All Databases) Unified 3-Way Decisions

Unified Metadata-First Architecture
Every query goes through metadata first. For EACH document, the LLM makes a 3-way decision:
  • answered: Finding from metadata (summary + chunks) is sufficient
  • irrelevant: Document not relevant to the query
  • needs_deep_research: Document likely relevant but needs full content analysis
Key Benefits: LLM sees actual metadata before deciding (not blind guessing). Per-document decisions enable programmatic reference building.

The 3-Way Decision Model

answered

The document's summary and top chunks contain sufficient information to answer the research question.

Returns: finding, page_reference (optional), confidence

irrelevant

The document is not relevant to the research statement based on its metadata.

Returns: (nothing - just status)

needs_deep_research

The document appears relevant but metadata doesn't have enough detail. Needs full document analysis.

Returns: research_hint (why)

Key Design: The LLM makes decisions AFTER seeing actual document metadata - not blindly upfront. This is more accurate than having the clarifier pre-guess whether "deep research" is needed.

Step-by-Step Execution

1
Fetch All Documents

All documents from the specified database are fetched with full summaries and top chunks.

SELECT m.id AS document_id, m.document_name, m.document_summary, -- Full summary m.document_type, m.page_count, m.file_name, 1 - (m.summary_embedding <=> CAST(:embedding AS vector)) AS similarity_score FROM iris_document_metadata m WHERE m.db_source = :db_source AND m.summary_embedding IS NOT NULL ORDER BY similarity_score DESC -- No LIMIT - fetch all, batching handles token management

Top Chunks Per Document

SELECT c.chunk_content, c.page_number, 1 - (c.chunk_embedding <=> CAST(:embedding AS vector)) AS chunk_similarity FROM iris_document_chunks c WHERE c.document_id = :doc_id AND c.chunk_embedding IS NOT NULL ORDER BY chunk_similarity DESC LIMIT :top_chunks_in_metadata -- Default: 3
2
Batch Processing (Parallel)

Documents are split into batches and processed in parallel.

# Batch creation batches = [all_documents[i:i + batch_size] for i in range(0, len(all_documents), batch_size)] # Example: 45 documents, batch_size=10 → 5 batches # Batch 1: docs 1-10 ┐ # Batch 2: docs 11-20 │ Processed in parallel # Batch 3: docs 21-30 │ (up to max_parallel_batches) # Batch 4: docs 31-40 │ # Batch 5: docs 41-45 ┘ with ThreadPoolExecutor(max_workers=max_parallel_batches) as executor: futures = [executor.submit(process_batch_unified, batch) for batch in batches]
Config Key Default Description
batch_size 10 Documents per batch
max_parallel_batches 5 Maximum concurrent batches
top_chunks_in_metadata 3 Top chunks fetched per document
3
Per-Document 3-Way Decisions

For each batch, the LLM makes a 3-way decision for every document using the return_unified_decisions tool.

Tool Definition

{ "name": "return_unified_decisions", "parameters": { "document_decisions": [ { "document_id": "uuid", // MUST match exactly what was sent "status": "answered | irrelevant | needs_deep_research", "finding": "...", // If answered "page_reference": 5, // Optional, if answered "confidence": "high | medium | low", // If answered "research_hint": "..." // If needs_deep_research } ] } }

Example Response

{ "document_decisions": [ { "document_id": "abc-123", "status": "answered", "finding": "The CAPM discount rate for Q2 2024 is 8.5% based on...", "page_reference": 12, "confidence": "high" }, { "document_id": "def-456", "status": "irrelevant" }, { "document_id": "ghi-789", "status": "needs_deep_research", "research_hint": "Summary mentions rate methodology but lacks specific values" } ] }
4
Build Response and Reference Index

Decisions are validated, then response and references are built programmatically from answered findings.

Validation

  • Filter to only document_ids we actually sent
  • Invalid status values default to needs_deep_research (safer)
  • Missing documents default to needs_deep_research

Programmatic Reference Building

# References are built from KNOWN document metadata # NOT from LLM-generated text (which is error-prone) for decision in answered_decisions: doc = documents[decision.document_id] reference_index[str(ref_num)] = { "doc_name": doc.document_name, # From our database "page": decision.page_reference, # From LLM (validated) "file_link": doc.file_name, # From our database "finding": decision.finding } ref_num += 1
Why Programmatic References? When sending 10 documents in a batch, we know exactly which document each finding is about via document_id. This lets us build accurate reference links from our database metadata, rather than relying on the LLM to correctly format document names in its response text.

Output: UnifiedMetadataResult

Field Type Description
answered_findings List[DocumentDecision] All documents with status="answered" (includes finding, page_ref, confidence)
needs_research_doc_ids List[str] Document IDs with status="needs_deep_research" (for Stage 2)
irrelevant_count int Count of documents marked irrelevant
answered_response str Formatted response text from answered findings with [REF:N] markers
answered_reference_index Dict[str, ReferenceEntry] Reference index keyed by "1", "2", etc.

What Happens Next (In Database Router)

Metadata Result Received

answered_response + answered_reference_index + needs_research_doc_ids
↓

Initialize Combined Response

Start with answered_response
Copy answered_reference_index
↓

Check needs_research_doc_ids

if needs_research_doc_ids: → Trigger File Research
else: → Return answered response directly
↓

File Research (Stage 2) - If Needed

Fetch all chunks for needs_research_doc_ids
LLM synthesizes page-level findings
Reference numbers continue: REF:N+1, REF:N+2, ...
↓

Merged Final Response

Metadata findings + File research findings
Combined reference_index (REF:1 through REF:M)
Reference Merging Example:
  • Metadata answered 3 docs: REF:1, REF:2, REF:3
  • File research for 2 docs: REF:4, REF:5, REF:6, REF:7
  • Final reference_index: keys "1" through "7"

Configuration (from Database Registry)

Configuration is loaded from iris_database_registry.research_config at runtime:

# From iris_database_registry.research_config JSONB { "batch_size": 10, // Documents per batch "max_parallel_batches": 5, // Concurrent batch processing "max_selected_files": 20, // Cap for file research "top_chunks_in_metadata": 3, // Top chunks per document "max_parallel_files": 5, // (Used by file research) "max_chunks_per_file": 20 // (Used by file research) }
Per-Database Config: Each database in iris_database_registry can have its own research_config values, allowing different batch sizes or chunk counts per database.
