Stage 4: Planner Agent

Database selection — determines which databases to query based on the research statement

When is this called? Only when the Clarifier Agent (Stage 3) returns proceed_with_research. Receives the research statement and selects relevant databases.

Step-by-Step Execution

1
Document Metadata Similarity Search

The planner performs a vector similarity search to find relevant documents before making the database selection.

Step 1a: Generate Query Embedding

Parameter Value
Input Research statement from Clarifier
Model config.get_model_config("embedding")
Dimensions 2000

Step 1b: Vector Similarity Search

SELECT db_source, document_name, document_summary, document_type, 1 - (summary_embedding <=> CAST(:embedding AS vector)) AS similarity_score FROM iris_document_metadata WHERE summary_embedding IS NOT NULL AND db_source IN (:available_databases) ORDER BY similarity_score DESC LIMIT :top_k
Parameter Value
Table iris_document_metadata
Similarity Method Cosine distance via pgvector <=> operator
Score Formula 1 - cosine_distance (higher = more similar)
Filter Only available_databases (user's accessible DBs)
top_k METADATA_SEARCH_TOP_K = 5

Output Fields

Field Description
db_source Database identifier (e.g., "internal_par")
document_name Document filename
document_summary Full document summary (used for context)
document_type File type (e.g., "pdf", "xlsx")
similarity_score 0.0 to 1.0 (higher = more relevant)
2
Load Prompts from Database
Parameter Value
Table iris_prompts
Filter layer = 'agent' AND name = 'planner'
Special Flag filtered_database=True — includes database descriptions in system prompt
Fields Retrieved system_prompt, tool_definition, user_prompt
Database Descriptions in System Prompt: The system prompt is composed with descriptions of each available database, helping the LLM understand what content is in each database.
3
Dynamic Enum Injection

The tool definition stored in the database has a placeholder structure. At runtime, we inject the actual available database keys:

Before Injection (from database)

{ "function": { "name": "select_databases", "parameters": { "properties": { "databases": { "type": "array", "items": { "type": "string", "enum": [] ← placeholder }, "maxItems": null ← placeholder } } } } }

After Injection (sent to LLM)

{ "function": { "name": "select_databases", "parameters": { "properties": { "databases": { "type": "array", "items": { "type": "string", "enum": ["internal_par", "internal_capm", "external_fred"] }, "maxItems": 3 ← from config.MAX_DATABASES_PER_QUERY } } } } }
Injected Value Source
enum array list(available_databases.keys())
maxItems config.MAX_DATABASES_PER_QUERY
4
Build User Message
Placeholder Replaced With

Output

Field Type Description
databases string[] List of database keys to query (validated against available_databases)
query_embedding float[] Pre-computed embedding vector (2000 dimensions) for reuse by downstream subagents
// Example output { "databases": ["internal_par", "internal_capm"], "query_embedding": [0.0123, -0.0456, ...] // 2000 floats }
Embedding Reuse: The planner generates the query embedding once during its metadata search. This embedding is returned in the output and passed to downstream subagents, avoiding redundant embedding API calls for each database query.

What Happens Next

For each database in the output list, the system executes the Cascading Retrieval with the path determined by the Clarifier's require_deep_research flag:
  • Stage 5: Metadata Subagent — uses the pre-computed query_embedding for vector similarity search, processes documents in batches (configurable batch_size, default 50)
  • If require_deep_research=false: Metadata Synthesis path — synthesizes answer from document summaries and top chunks, returns directly
  • If require_deep_research=true: Catalog Selection path — selects relevant files (up to max_selected_files, default 20), then calls Stage 6: File Research Subagent for full document analysis
Selected databases are queried in parallel, all sharing the same embedding. Batch size and file limits are configured per-database in iris_database_registry.research_config.

Available Databases Example

The available_databases dictionary contains database configurations. Here's an example structure:

internal_par Policies & Reserves documentation
internal_capm CAPM methodology documents
internal_ecl Expected Credit Loss policies
external_fred Federal Reserve economic data

Decision Logic

How the LLM selects databases:
  • Matches research statement keywords to database descriptions
  • Uses document_metadata_context hints if available
  • Prefers internal sources for policy/methodology questions
  • May select multiple databases for cross-referencing
  • Limited by maxItems constraint

Selection Examples
