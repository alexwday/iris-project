4. Model Structure and Approach

Model Name: IRIS (Intelligent Research and Information System) Model ID: IRIS-001

4.1 Approach Selection

IRIS leverages large language models for both generative capabilities and embedding functions within a Retrieval-Augmented Generation (RAG) framework. Our approach to model selection was primarily driven by the models available within RBC's infrastructure:

  1. Model Selection Constraints:
  2. Limited to models available through RBC's Lumina portal (GPT-3.5, GPT-4, GPT-4-turbo, GPT-4o-mini, GPT-4o)
  3. On-premises options (Llama, Qwen, Cohere) for specific use cases
  4. Not training our own models, focusing instead on optimal use of commercial options
  5. Performance on public benchmarks and leaderboards (MMLU, TruthfulQA)
  6. Context window length requirements to handle large documents

  7. Processing speed and cost efficiency considerations

  8. Validation through internal testing:

  9. Initial samples provided to the APG team for feedback
  10. Internal review to confirm model sufficiency
  11. Assessment of response quality and accuracy for finance-specific queries
  12. Evaluation of citation quality and source attribution

Based on these constraints and evaluations, we selected GPT-4o-mini for quick decision-making and contexts where all necessary information is provided, GPT-4o for more important decisions and final response generation, and text-embedding-3-large for our embedding model. For visual content processing (infographics, images), we employ an on-premises hosted version of Qwen2 7B VL. For external data that cannot be redistributed, we use an on-premises version of Cohere command-north-large.

IRIS implements a modular, agent-based architecture with a hybrid RAG approach. The system processes user queries through a sequential pipeline with two primary processing paths:

  1. Direct Response Path: For queries that can be answered using only conversation history

  2. Agent Router → Agent Direct Response

  3. Research Path: For queries requiring database research

  4. Agent Router → Agent Clarifier → Agent Planner → Database Subagents → Agent Summarizer

Our agent-based approach was designed to be both conversational (using conversation history for context) and autonomous (searching specific databases as needed instead of all content at once). The architecture enables strategic querying of selected databases rather than querying all databases for every question, significantly improving efficiency and relevance.

After experimenting with multiple Retrieval-Augmented Generation (RAG) methods, we developed a hybrid approach with five document processing pipelines for input and three specific retrieval methods:

Five Input Processing Pipelines:

  1. Catalog Search - Small: Standard pipeline for processing normal documents (PDF, DOCX) that converts content to markdown and generates metadata.

  2. Catalog Search - Vision: Specialized pipeline for processing infographics and visual documents using Qwen2 vision model to extract text, diagrams, and visual elements into markdown.

  3. Catalog Search - Excel: Custom pipeline for converting Excel spreadsheets with structured data into markdown documents with preserved table formatting.

  4. Catalog Search - Large: Pipeline for processing large documents with distinct sections, creating both document-level and section-level summaries.

  5. Semantic Search - Large: Pipeline for very large reference documents that includes chunking, embedding generation, and metadata enrichment.

Three Retrieval Methods:

  1. Catalog Search - Small: For documents processed through the Small, Vision, or Excel pipelines (under 10,000 tokens), we send entire documents within the context window rather than chunking. The model selects relevant documents from a catalog based on descriptions and metadata.

  2. Catalog Search - Large: For larger documents with distinct sections, we implement a two-stage retrieval process where the model first selects relevant documents from a catalog and then identifies specific sections within those documents.

  3. Semantic Search - Large: For very large reference documents like accounting standards, we implement vector embedding similarity search with sophisticated reranking and section expansion. This method performs similarity matching with query embeddings, reranks results based on relevance criteria, and expands selected sections to maintain context.

We select the optimal input pipeline and retrieval method for each database based on document type and structure. This multi-tiered approach allows us to handle various document types optimally rather than applying a one-size-fits-all solution, resulting in more accurate and relevant responses.

We evaluated several alternative approaches before selecting our hybrid architecture:

  1. Basic RAG: Standard retrieval-augmented generation doesn't apply equally well to varying document types. Tuning for one database might work well but wouldn't be an apply-all solution. This approach would also require querying all databases for every question rather than strategic querying.

  2. Pure LLM Approach: Using a large language model alone would risk providing information not backed by official policy documentation and make source attribution difficult, making it inappropriate for financial policy guidance where attribution is essential.

  3. Single-Stage Processing: A non-agent approach would limit the system's ability to make strategic decisions about information retrieval and would reduce transparency in the reasoning process.

The selected approach aligns with the model's purpose of providing accurate, policy-compliant guidance based on authorized knowledge sources while maintaining transparency and efficiency.

Database Refresh Pipeline Models:

These models were selected based on their strong performance on finance-specific benchmarks and their ability to provide reliable outputs while mitigating misinformation risks compared to smaller or less capable models.

4.2 Model Inputs

IRIS uses a streamlined input approach centered around conversation history and structured database content. The key inputs include:

  • Conversation History: The primary input is the complete conversation history, including the current user query and all previous exchanges. This history provides essential context for understanding the current query and enables continuity in multi-turn conversations, especially for follow-up questions or references to previously discussed topics.

  • PostgreSQL Database Content: The system connects directly to PostgreSQL tables (as defined in the postgres_schema.sql file) that store processed document content and metadata. These tables provide the knowledge base from which relevant information is retrieved during the research process.

  • Specialized System Prompts: Throughout the processing pipeline, carefully crafted system prompts are injected to guide each LLM component. These prompts define the role and expected output format for each agent and vary based on the specific task (routing, clarification, planning, etc.).

The agent architecture processes the conversation history by strategically injecting specialized system prompts at each stage and incorporating relevant content retrieved from the PostgreSQL database as context for the LLM. This approach allows the system to maintain conversation context while providing accurate, document-grounded responses to finance and accounting policy inquiries.

Our solution leverages industry best practices and public benchmarking/leaderboard results to select appropriate models and approaches. The hybrid approach, with its flexible document processing and retrieval methods, worked effectively with minimal adjustments beyond tuning prompts and optimizing database storage.

Limitations of the Modeling Approach

While our generative model is chosen based on its strong reasoning capabilities, it is not without limitations. There are instances when the model may not fully grasp extremely specialized finance or accounting concepts. However, these instances are not very frequent, and users are made aware of the risks and limitations through the Maven user interface.

Assumptions and Conditions for Revisiting

Assumptions made for the model's efficacy are designed to bolster its reliability and quality of outputs across finance and accounting policy contexts. These assumptions will be scrutinized if:

  1. Significant changes to the knowledge base structure or content occur
  2. New types of documents with different formatting or organization are added
  3. The system expands to new subject domains beyond finance and accounting
  4. User requirements or usage patterns change significantly
  5. Advances in LLM capabilities enable new approaches

Confidentiality and Information Filtering

Our models operate within RBC's secure environment, and data is not modified before being processed by the ML models. The data (queries and responses) are kept for audit and monitoring purposes. No user query data is used for model training.

Design Approach

Our approach focused on implementing best practices from industry trends and leveraging techniques that have demonstrated success in public benchmarks and leaderboards. Rather than conducting extensive comparative testing, we selected approaches that aligned with our document types and system requirements. The hybrid approach with specialized processing pipelines required minimal tuning to achieve satisfactory results, with most adjustments focused on prompt engineering and database optimization.
