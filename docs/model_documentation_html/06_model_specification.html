Model Specification

This section describes the IRIS model methodologies and processing components, focusing on the agent-based architecture, query processing mechanisms, and mathematical foundations of information retrieval and synthesis.

6.1 Agent Architecture

The IRIS system implements a modular, pipeline-based architecture consisting of specialized AI agents that process user queries through a structured workflow. The overall architecture contains two primary processing paths managed by a central model orchestration engine:

6.1.1 Processing Pathways

  1. Direct Response Path
  2. Used for queries that can be answered using only conversation history
  3. Processing sequence: agent_router → agent_direct_response

  4. Optimized for contextual queries that don't require additional research

  5. Research Path

  6. Used for queries requiring database research
  7. Processing sequence: agent_router → agent_clarifier → agent_planner → database_subagents → agent_summarizer
  8. Implements a comprehensive retrieval-augmented generation approach

6.1.2 Agent Components and Functions

Agent Function Mathematical/Algorithm Basis
Router Agent Determines processing path based on query analysis Classification algorithm using transformer-based embeddings with context-aware decision boundary
Clarifier Agent Assesses query context sufficiency and creates research statements Information-theoretic query expansion with controlled relevance parameters
Planner Agent Selects optimal databases for query execution Multi-class relevance scoring with database-specific prior weightings
Database Subagents Retrieve and pre-process information from various data sources Implemented through five distinct processing methodologies (detailed in Section 6.2)
Summarizer Agent Integrates findings and generates coherent responses Multi-document extraction-abstraction mechanism with attention-based relevance weighting
Direct Response Agent Generates responses using only conversation history Constrained inference with context-window utilization optimization

6.1.3 System Integration

The central chat model orchestration component (model.py) serves as the integration hub, managing:

  1. System initialization and configuration
  2. Query routing based on router agent decisions
  3. Sequential and parallel agent execution flow
  4. Result aggregation and presentation
  5. Process monitoring and error handling

6.2 Database Retrieval Methodologies

The IRIS system implements five distinct database retrieval methodologies, each optimized for different types of source documents:

6.2.1 Catalog Search - Small

Mathematical Specification: * Two-stage selection with catalog prioritization * Document assessment function: $R_{LLM}(d, q) \rightarrow {d_1, d_2, ..., d_n}$ representing LLM-selected documents * Document selection is modeled as: $D_{selected} = LLM_{select}(catalog, q)$ where the LLM selects documents based on title and description * Response synthesis: $R_{synthesis} = LLM_{synthesize}({content(d) | d \in D_{selected}}, q)$

Implementation: 1. Catalog Retrieval: Query PostgreSQL for document metadata using SQL: sql SELECT id, document_name, document_description FROM apg_catalog WHERE document_source = 'internal_par' ORDER BY document_name 2. Document Selection: LLM-based selection (GPT-4o-mini with temperature 0.2): * Format catalog with document IDs, names, and descriptions * Pass to LLM with selection prompt * Parse returned JSON list of document IDs * Fallback regex extraction if JSON parsing fails 3. Content Retrieval: Fetch complete document content for selected IDs: sql SELECT section_id, section_name, section_content FROM apg_content WHERE document_source = 'internal_par' AND document_name = %s ORDER BY section_id 4. Response Synthesis: Generate research report using tool call (GPT-4o with temperature 0.2): * Format documents with hierarchical structure: # Document Name → ## Section Name → Content * Tool call returns both status_summary and detailed_research * Citations include document name and section name

Application: * Used for standard documents (PDF, DOCX) with simple structure * Example databases: internal_par, internal_process_and_controls

6.2.2 Catalog Search - Large

Mathematical Specification: * Three-stage hierarchical selection using LLM judgment * Document selection: $D_{selected} = LLM_{select}(catalog, q)$ where the LLM selects relevant documents * Section selection: $S_{selected,d} = LLM_{select}(sections(d), q)$ for each $d \in D_{selected}$ * Final synthesis: $R_{synthesis} = LLM_{synthesize}({content(s) | s \in \bigcup_{d \in D_{selected}} S_{selected,d}}, q)$

Implementation: 1. Catalog Retrieval: Same SQL query pattern as Catalog Search - Small but for CAPM sources 2. Document Selection: LLM-based selection (GPT-4o-mini with temperature 0.2): * Same process as Catalog Search - Small * Returns list of document IDs from the catalog 3. Section Summary Retrieval: Additional intermediate step: sql SELECT section_id, section_name, section_summary FROM apg_content WHERE document_source = 'internal_capm' AND document_name = %s ORDER BY section_id 4. Section Selection: LLM-based selection of specific sections (GPT-4o-mini): * Format document sections and their summaries * LLM selects specific section IDs for each document based on relevance to query * Returns dictionary mapping document names to lists of section IDs 5. Content Retrieval: Fetch only selected sections: sql SELECT section_id, section_name, section_content FROM apg_content WHERE document_source = 'internal_capm' AND document_name = %s AND section_id IN (%s, %s, ...) ORDER BY section_id 6. Response Synthesis: Same tool-calling approach as Catalog Search - Small

Application: * Used for large documents with distinct sections/chapters * Example databases: internal_capm, internal_global_finance_standards

6.2.3 Catalog Search - Excel

Mathematical Specification: * Table preprocessing with row-level document conversion * Each row/grouping $r$ is transformed to document $d_r$ by function $T_{excel}(r) = d_r$ * Document selection through LLM assessment: $D_{selected} = LLM_{select}(catalog, q)$ where each catalog entry represents a processed row/table

Implementation: 1. Pre-Processing: Excel files are processed during database creation: * Excel content is extracted and converted to Markdown format * Each table or logical row grouping becomes a separate document * Tables are preserved with Markdown formatting 2. Database Query: After pre-processing, same implementation as Catalog Search - Small: * Document selection via LLM from catalog * Content retrieval for selected documents * Response synthesis using GPT-4o tool call

Application: * Used for Excel spreadsheets and tabular data * Example databases: internal_wiki, internal_management_reporting

6.2.4 Catalog Search - Vision

Mathematical Specification: * Image-to-text conversion using multi-pass vision transformer * Image content extraction: $T_{vision}(i) = d_i$ where $i$ is an image and $d_i$ is the extracted text document * Document selection through LLM assessment: $D_{selected} = LLM_{select}(catalog, q)$

Implementation: 1. Pre-Processing: Infographics are processed during database creation: * Images are processed via Qwen2 vision model in multi-pass mode * Multiple extraction passes: text, tables, charts, diagrams * Content is converted to structured Markdown format * Each infographic becomes a document in the database 2. Database Query: After pre-processing, identical implementation to Catalog Search - Small: * Document selection via LLM from catalog (GPT-4o-mini) * Content retrieval for selected documents * Response synthesis using GPT-4o tool call (temperature 0.2)

Application: * Used for infographics and image-based documents * Example database: internal_cheatsheets

6.2.5 Semantic Search - Large

Mathematical Specification: * Vector-based similarity search with token-aware chunking * Chunk embedding: $E(c) = \vec{v_c}$ where $c$ is a chunk and $\vec{v_c}$ is its embedding vector * Query embedding: $E(q) = \vec{v_q}$ * Initial similarity scoring: $sim(c, q) = 1 - (c.embedding <=> q.embedding)$ using the PostgreSQL vector operator * Initial chunk selection: $C_{initial}(q) = top_k(C, sim, k)$ where $k = 20$ (INITIAL_K constant) * Relevance filtering: $C_{filtered} = {c \in C_{initial} | LLM_{relevance}(c.summary, q) = 1}$ * Importance reranking: $score(c) = sim(c, q) \cdot (1 + IMPORTANCE_FACTOR \cdot c.importance_score)$ where $IMPORTANCE_FACTOR = 0.2$ * Section expansion: Expand sections with tokens $\leq THRESHOLD$ (with different thresholds based on rank) * Gap filling: Fill sequence gaps where $0 < gap \leq MAX_SEQUENCE_GAP$ (where $MAX_SEQUENCE_GAP = 8$)

Implementation: 1. Query embedding generation: Using text-embedding-3-large (2000 dimensions) to create a dense vector representation of the query 2. Initial vector similarity search: Retrieval of top-20 (INITIAL_K) most similar chunks by cosine similarity using PostgreSQL vector extension with the query: sql SELECT c.*, 1 - (c.embedding <=> %s::vector) AS vector_score FROM iris_textbook_database c WHERE c.document_id = %s ORDER BY vector_score DESC LIMIT %s; 3. Summary relevance filtering: LLM-based classification of chunk summaries as relevant (1) or irrelevant (0): * Uses GPT-4o-mini (temperature 0.2) to classify each chunk's summary * Removes chunks classified as irrelevant (0) * Keeps original rank order from vector similarity 4. Importance-based reranking: * Applies formula: $score = vector_score \cdot (1 + 0.2 \cdot section_importance_score)$ * Sorts results by new score (descending) * Assigns new rank based on this ordering 5. Section expansion by token count: * For top 5 ranked chunks: Expands if section token count ≤ 8000 tokens * For other chunks: Expands if section token count ≤ 4000 tokens * Fetches all chunks from the same section when expansion criteria are met * Groups chunks from the same section together 6. Sequence gap filling: * Identifies sequence gaps between consecutive chunks ≤ 8 sequence numbers * Fills these gaps by retrieving the intermediate chunks * Assigns importance scores based on averaging adjacent chunks 7. Card formatting and response synthesis: * Formats all chunks into "cards" with metadata and content * Generates comprehensive research report using GPT-4o (temperature 0.7) * Synthesis must include inline citations from the source material

Application: * Used for very large documents and external sources * Example databases: external_ey, external_iasb, external_kpmg, external_pwc

6.3 Model Decision Processes

6.3.1 Router Decision

Mathematical Specification: * Binary classification: $f_{route}(q, c) \in {direct, research}$ * Where $q$ is the query and $c$ is the conversation context

Implementation: 1. Input: User query and conversation history 2. Process: LLM-based analysis using GPT-4o-mini with structured tool output 3. Output: Function name to invoke (response_from_conversation or research_from_database) 4. Parameters: temperature=0.1 (low randomness to ensure consistency)

6.3.2 Clarifier Decision

Mathematical Specification: * Context sufficiency assessment: $sufficiency(q, c) \in [0, 1]$ * Research formulation: $r = formulate(q, c)$ if $sufficiency(q, c) > \theta_{context}$

Implementation: 1. Input: User query, conversation history, and router decision 2. Process: LLM-based analysis using GPT-4o with structured output 3. Output: * Context questions (if insufficient context) * Research statement (if sufficient context) * Research scope (metadata or research)

6.3.3 Database Selection

Mathematical Specification: * Multi-class relevance scoring: $relevance(db, r) \in [0, 1]$ for each database $db$ * Selection: $DB_{selected} = {db \in DB | relevance(db, r) > \theta_{relevance}}$

Implementation: 1. Input: Research statement from clarifier 2. Process: LLM-based analysis using GPT-4o-mini with structured output 3. Output: List of selected databases to query 4. Parameters: temperature=0.2 (low randomness with slight variability)

6.3.4 Response Synthesis

Mathematical Specification: * Multi-document extraction-abstraction: $synthesis(retrieved_content, r)$ * Where $retrieved_content$ represents the aggregated results from database queries

Implementation: 1. Input: Detailed research from multiple database subagents 2. Process: LLM-based synthesis using GPT-4o 3. Output: Coherent, cited research summary 4. Parameters: temperature=0.4 (balanced between creativity and consistency)

6.5 Numerical Methods and Approximations

6.5.1 Tokenization

  • Tokenizer: tiktoken (cl100k_base)
  • Token thresholds:
  • Context window management: Dynamic truncation based on token counts
  • Chat history: Maintains last 10 messages within token limit
  • Document chunking: 250-750 tokens per chunk (depending on semantic boundaries)

6.5.2 Token-Aware Chunking Algorithm

Section-aware chunking implements a numerical approximation for optimal information density through a hierarchical sectional chunking process:

Mathematical Formulation: * Let $D$ represent a document consisting of sections $S = {s_1, s_2, ..., s_n}$ * For each section $s_i$, calculate token count $T(s_i)$ * Define threshold parameters $T_{min} = 250$ and $T_{max} = 750$ * The chunking process can be expressed as a sequence of operations: * If $T(s_i) < T_{min}$: Merge with adjacent section $s_{i+1}$ if $T(s_i) + T(s_{i+1}) \leq T_{max}$ * If $T(s_i) > T_{max}$: Split into subsections ${s_{i,1}, s_{i,2}, ..., s_{i,k}}$ such that $T_{min} \leq T(s_{i,j}) \leq T_{max}$ for all $j \in {1,2,...,k}$ * If $T_{min} \leq T(s_i) \leq T_{max}$: Maintain as a standalone chunk

Implementation Process: 1. The system traverses the document structure hierarchically, beginning with major sections 2. For each section, the tokenizer calculates precise token counts using tiktoken 3. Section boundaries are preserved where possible to maintain semantic coherence 4. When sections exceed the maximum token threshold, the system splits at paragraph boundaries 5. When sections are below the minimum threshold, they are merged with adjacent sections 6. Merged sections are continuously evaluated against the maximum threshold 7. The final chunking preserves the document's logical flow while maintaining optimal chunk sizes

This approach balances information density with semantic coherence, ensuring that related content remains together while maintaining manageable chunk sizes for embedding and retrieval.

6.5.3 Embedding Batch Processing

To optimize embedding generation, the system implements vector batch processing through a parallelized computation architecture:

Mathematical Formulation: * Given a set of chunks $C = {c_1, c_2, ..., c_m}$ * Define batch size $B = 50$ * Partition $C$ into batch sets $B_i = {c_{i \cdot B + 1}, c_{i \cdot B + 2}, ..., c_{min((i+1) \cdot B, m)}}$ for $i \in {0, 1, ..., \lceil m/B \rceil - 1}$ * Apply embedding function $E$ to each batch: $E(B_i) = {E(c) | c \in B_i}$ * The complete embedding set is the union: $E(C) = \bigcup_{i=0}^{\lceil m/B \rceil - 1} E(B_i)$

Implementation Process: 1. The system divides the total chunk collection into batches of 50 chunks each 2. Each batch is submitted to the embedding API as a single request 3. The embedding model (text-embedding-3-large) processes each chunk in the batch 4. Returned embeddings are stored with their corresponding chunk IDs 5. The system monitors embedding generation for quality and consistency 6. Embeddings are stored in the PostgreSQL database using the pgvector extension

This batched approach significantly improves throughput by reducing API overhead while maintaining embedding quality and consistency.

6.5.4 Similarity Scoring

Vector similarity is calculated using cosine similarity:

$$sim(v_1, v_2) = \frac{v_1 \cdot v_2}{||v_1|| \cdot ||v_2||}$$

Where $v_1$ and $v_2$ are embedding vectors for chunks or queries.
