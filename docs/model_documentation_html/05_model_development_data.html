5. Model Development Data

5.1 Data Validity and Sources

The IRIS system retrieves information from a collection of internal and external accounting and finance knowledge sources stored in a PostgreSQL database. This section describes the data used by the system, its sources, and processing methods.

Data Coverage and Scope

IRIS accesses data covering the following domains:

  • Internal RBC Policies: Corporate Accounting Policy Manuals (CAPMs), process documentation, and control frameworks
  • Accounting Guidelines: CFO and APG-developed guides, cheatsheets, and wiki entries
  • Internal Documentation: Accounting memos, project approval requests, and finance-related guidance
  • Financial Reporting: Management reporting policies and external reporting requirements
  • Accounting Standards: IFRS standards and interpretations from select accounting firms (EY, KPMG, PwC)

This domain-focused coverage enables IRIS to address finance and accounting inquiries relevant to the CFO Group.

Data Storage and Management

The system stores processed documents in a PostgreSQL database with a structured schema designed to support both catalog-based and semantic search approaches. The database consists of three primary tables:

1. apg_catalog: Document Metadata Repository

CREATE TABLE apg_catalog (
    -- System Fields
    id SERIAL PRIMARY KEY,                        -- Auto-incrementing unique identifier
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), -- When the record was added to the database

    -- Document Identification Fields
    document_source VARCHAR(100) NOT NULL,        -- Source of the document (e.g., 'internal_capm', 'external_iasb')
    document_type VARCHAR(100) NOT NULL,          -- Type of document (e.g., 'capm', 'infographic', 'memo')
    document_name VARCHAR(255) NOT NULL,          -- Formatted document name (e.g., 'IFRS 9 - Financial Instruments')

    -- Scope Fields
    document_description TEXT,                    -- Original AI-generated description of document usage/scope
    document_usage TEXT,                          -- Field for LLM selection/usage guidance

    -- Refresh Metadata Fields
    date_created TIMESTAMP WITH TIME ZONE,        -- Original document creation date
    date_last_modified TIMESTAMP WITH TIME ZONE,  -- Date the document was last modified
    file_name VARCHAR(255),                       -- Full filename with extension (e.g., 'IFRS9_Financial_Instruments.pdf')
    file_type VARCHAR(50),                        -- File extension/type (e.g., '.pdf', '.docx', '.xlsx')
    file_size BIGINT,                             -- Size of the file in bytes
    file_path VARCHAR(1000),                      -- Full system path to the original file
    file_link VARCHAR(1000)                       -- URL or NAS path to the file
)

2. apg_content: Document Content Storage

CREATE TABLE apg_content (
    -- System Fields
    id SERIAL PRIMARY KEY,                        -- Auto-incrementing unique identifier
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), -- When the record was added to the database

    -- Document Reference Fields (matching catalog)
    document_source VARCHAR(100) NOT NULL,        -- Source of the document (matches apg_catalog)
    document_type VARCHAR(100) NOT NULL,          -- Type of document (matches apg_catalog)
    document_name VARCHAR(255) NOT NULL,          -- Document name (matches apg_catalog)

    -- Content Fields
    section_id INTEGER NOT NULL,                  -- Ordered sequence number within the document
    section_name VARCHAR(500),                    -- Title of the section/chapter
    section_summary TEXT,                         -- AI-generated summary of the section
    section_content TEXT NOT NULL                 -- The actual content of the section
)

3. iris_textbook_database: Vector Embeddings Store

CREATE TABLE iris_textbook_database (
  -- SYSTEM FIELDS
  id SERIAL PRIMARY KEY,  -- Unique identifier for each chunk
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),  -- Record creation timestamp

  -- STRUCTURAL POSITIONING FIELDS
  document_id TEXT,                 -- E.g., "IFRS_Handbook_2023" or "EY_GAAP_Guide_2024"
  chapter_number INT,              -- E.g., 4
  section_number INT,              -- E.g., 2
  part_number INT,                 -- E.g., 1
  sequence_number INT,             -- E.g., 14 (position in chunk order)

  -- CHAPTER-LEVEL METADATA
  chapter_name TEXT,               -- E.g., "Leases" or "Revenue Recognition"
  chapter_tags TEXT[],             -- E.g., {"Financial_Instruments", "Disclosure_Requirements"}
  chapter_summary TEXT,            -- E.g., "This chapter explains revenue recognition..."
  chapter_token_count INT,         -- Total token count across the full chapter

  -- SECTION-LEVEL PAGINATION & IMPORTANCE
  section_start_page INT,          -- E.g., 142 (start page of section)
  section_end_page INT,            -- E.g., 143 (end page of section)
  section_importance_score FLOAT,  -- E.g., 0.85 (importance of this section)
  section_token_count INT,         -- Total token count for this section

  -- SECTION-LEVEL METADATA
  section_hierarchy TEXT,          -- E.g., "Chapter 4 > Section 4.2 > Subsection 4.2.3"
  section_title TEXT,              -- E.g., "Identification of Separate Performance Obligations"
  section_standard TEXT,           -- E.g., "IFRS", "US_GAAP", "AASB"
  section_standard_codes TEXT[],   -- E.g., {"IFRS 16", "IAS 17", "IFRS 9"}
  section_references TEXT[],       -- E.g., {"Section 3.4", "IAS 36 Para 12-15"}

  -- CONTENT & EMBEDDING
  content TEXT NOT NULL,           -- The actual textbook content in this chunk
  embedding VECTOR(2000),          -- OpenAI's text-embedding-3-large model vector
  text_search_vector TSVECTOR GENERATED ALWAYS AS (to_tsvector('english', content)) STORED
)

4. process_monitor_logs: Performance Monitoring and Logging System

CREATE TABLE process_monitor_logs (
    -- Core Fields
    log_id BIGSERIAL PRIMARY KEY,                -- Auto-incrementing unique ID for each log entry
    run_uuid UUID NOT NULL,                      -- Unique ID generated for each model invocation
    model_name VARCHAR(100) NOT NULL,            -- Identifier for the model
    stage_name VARCHAR(100) NOT NULL,            -- Name of the specific process stage
    stage_start_time TIMESTAMPTZ NOT NULL,       -- Timestamp when the stage began
    stage_end_time TIMESTAMPTZ,                  -- Timestamp when the stage ended
    duration_ms INT,                             -- Duration of the stage in milliseconds
    llm_calls JSONB,                             -- JSON array storing details for LLM calls
    total_tokens INT,                            -- Sum of total tokens from all llm_calls
    total_cost DECIMAL(12, 6),                   -- Sum of costs from all llm_calls
    status VARCHAR(255),                         -- Outcome/Status of the stage
    decision_details TEXT,                       -- Specific outputs or decisions
    error_message TEXT,                          -- Detailed error message if the stage failed
    log_timestamp TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP -- Timestamp when log row was created
)

This table serves as an output destination where the model automatically logs performance metrics after each component execution, rather than an input source for the model.

Data Processing Framework

The document processing framework transforms source documents into formats optimized for the different retrieval methods:

  1. Source Identification: Documents are identified and retrieved from designated Network Attached Storage (NAS) locations
  2. Format Conversion: Documents from various formats (PDF, Word, Excel, images) are converted to standardized markdown text
  3. Structure Preservation: Document hierarchies, sections, and relationships are maintained during processing
  4. Metadata Generation: Document and section summaries are created to support retrieval decisions
  5. Storage Optimization: Content is stored in appropriate database tables based on document type

Metadata Generation Process

Each pipeline type employs a specialized metadata generation approach:

  1. Catalog Search - Small
  2. Uses GPT-4o to generate document usage summaries and descriptions
  3. Creates concise overviews of document purpose and applicability
  4. Focuses on document-level metadata to support catalog selection

  5. Produces standardized metadata fields for consistent retrieval

  6. Catalog Search - Large

  7. Includes all metadata generation from Catalog Search Small
  8. Additionally generates summaries for each defined section and chapter
  9. Creates hierarchical metadata reflecting document structure

  10. Enables more granular selection by allowing LLMs to refine searches to specific sections

  11. Catalog Search - Excel & Vision

  12. Follows the same metadata generation approach as Catalog Search Small
  13. For Excel: Preserves tabular structure with appropriate metadata

  14. For Vision: Uses Qwen2 model to extract and describe visual content before metadata generation

  15. Semantic Search - Large

  16. Employs an extensive recursive metadata generation process
  17. First generates comprehensive metadata at the chapter level including:
    • Chapter summaries
    • Applicable accounting standards
    • Key concepts and terminology
  18. Then uses this chapter-level context to recursively generate metadata for individual sections:
    • Section summaries
    • Contextual tags
    • Importance scores
    • Hierarchical positioning
  19. This rich metadata supports vector search, reranking, and context expansion operations

For documents requiring semantic search capabilities, additional processing generates vector embeddings using the text-embedding-3-large model (3072 dimensions) to support similarity-based retrieval.

5.2 Document Processing Pipelines

IRIS uses five specialized document processing pipelines, each optimized for specific document types and formats. These pipelines transform source documents into formats suitable for efficient retrieval.

Document Processing Approaches

  1. Catalog Search - Small: For standard documents (e.g., Project Approval Requests)
  2. Converts documents to markdown format
  3. Keeps documents whole without chunking
  4. Generates document-level summaries for catalog selection

  5. Suitable for documents under 10,000 tokens

  6. Catalog Search - Large: For large documents with distinct sections (e.g., Corporate Accounting Policy Manuals)

  7. Converts documents to markdown format
  8. Splits documents into logical sections based on headings
  9. Creates both document-level and section-level summaries

  10. Enables two-stage retrieval (document selection, then section selection)

  11. Catalog Search - Excel: For Excel spreadsheets (e.g., Wiki entries)

  12. Converts spreadsheet content to markdown with preserved table structures
  13. Processes each relevant row or group of rows as a separate entry

  14. Standardizes formatting for numerical data and table layouts

  15. Catalog Search - Vision: For infographics and visual content (e.g., cheatsheets)

  16. Uses Qwen2 vision model to process image content into structured markdown
  17. Extracts text, visual elements, and structural information

  18. Combines results into a single structured document with proper formatting

  19. Semantic Search - Large: For very large reference materials (e.g., IFRS Standards)

  20. Extracts text while preserving document structure
  21. Identifies chapters and sections with hierarchical relationships
  22. Creates optimally sized chunks for semantic search
  23. Generates comprehensive metadata at the chapter level:
    • Chapter summaries and key concepts
    • Applicable accounting standards
    • Usage guidance and applicability
  24. Uses chapter-level metadata as context to recursively generate section-level metadata:
    • Section summaries and contextual tags
    • Importance scores for prioritization
    • Hierarchical positioning information
  25. Generates vector embeddings using text-embedding-3-large model configured for 2000 dimensions
  26. Stores both content and metadata to support reranking and context expansion

Document Transformation Process

The document processing workflow includes several key transformation steps:

  1. Format Standardization
  2. Converts diverse document formats into consistent markdown text
  3. Preserves essential formatting elements (headings, tables, lists)

  4. Ensures consistent rendering across different document types

  5. Structure Preservation

  6. Maintains document hierarchies and section relationships
  7. Preserves heading levels to reflect document organization

  8. Retains connections between related document sections

  9. Metadata Enrichment

  10. Extracts and stores document and section metadata
  11. Generates AI-powered summaries using GPT-4o for retrieval optimization
  12. Preserves source information and hierarchical relationships
  13. Creates recursive metadata structures for semantic search documents

  14. Builds cross-referencing systems between related content sections

  15. Retrieval Optimization

  16. For catalog-based retrieval:

    • Generates high-quality document descriptions and usage summaries
    • Creates section-level summaries for large documents to enable refined selection
    • Structures metadata fields to support LLM-based document selection

  17. For semantic search:

    • Creates vector embeddings of document chunks using text-embedding-3-large
    • Generates positional and hierarchical metadata for reranking and context expansion
    • Implements importance scoring to prioritize more relevant sections
    • Preserves parent-child relationships between document sections
    • Pre-calculates token counts to optimize context usage

5.3 System Inputs and Database Structure

IRIS operates primarily on conversation history and content retrieved from its database structure. This section details the database design and inputs used by the system.

Database Structure

The PostgreSQL database consists of three primary tables:

Table: apg_catalog * Purpose: Stores metadata about available knowledge sources * Key fields: document_source, document_name, document_type, document_description * Contains information about document origin, purpose, and searchable descriptions

Table: apg_content * Purpose: Stores actual document content and section summaries * Key fields: document_source, document_name, section_id, section_name, section_summary, section_content * Used primarily for catalog-based search methods

Table: iris_textbook_database * Purpose: Stores vector representations for semantic search * Key fields: embedding (vector), content, section_hierarchy, section_importance_score * Contains rich metadata at chapter and section levels to support recursive context expansion * Includes structural positioning data (chapter, section, part numbers) * Stores information about applicable standards and references * Utilizes PostgreSQL vector extensions for similarity searching

Input Processing Flow

The IRIS agent architecture processes inputs through a sequential pipeline:

  1. Initial Input: The system receives the complete conversation history including the current user query and previous exchanges.

  2. Router Processing: The Agent Router analyzes the conversation to determine whether to:

  3. Use only conversation context (Direct Response path)

  4. Retrieve information from databases (Research path)

  5. Research Processing: For the research path, the system:

  6. Evaluates context sufficiency (Agent Clarifier)
  7. Determines relevant knowledge sources (Agent Planner)
  8. Retrieves information using appropriate search methods (Database Subagents)

  9. Synthesizes findings into coherent responses (Agent Summarizer)

  10. Specialized Prompting: Each agent uses carefully designed system prompts customized for its specific function, which guides the LLM's behavior and output format.

Model-Specific Inputs

The IRIS system primarily processes three types of inputs:

  1. Conversation History
  2. Complete user-system interaction records
  3. Current query and all previous exchanges

  4. Session context and follow-up information

  5. PostgreSQL Database Tables

  6. Structured document content from apg_content
  7. Document metadata from apg_catalog

  8. Vector embeddings and rich metadata from iris_textbook_database

  9. Specialized Prompts

  10. System prompts customized for each agent
  11. Specific function-oriented instructions
  12. Response format guidelines

Each component in the IRIS pipeline processes these inputs in specialized ways:

  • Agent Router: Processes conversation history to determine processing path
  • Agent Clarifier: Analyzes conversation context to ensure sufficient information
  • Agent Planner: Evaluates research needs to select appropriate knowledge sources
  • Database Subagents: Query PostgreSQL tables using specialized retrieval methods
  • Agent Summarizer: Integrates database findings into coherent responses

For semantic search capabilities, the embedding generation process uses text-embedding-3-large model configured to generate 2000-dimensional vectors (rather than its maximum 3072 dimensions) to fit PostgreSQL database limits, creating efficient vector representations of document chunks for similarity-based retrieval.

5.4 Data Assumptions and Limitations

The IRIS system operates under several data-related assumptions and limitations that affect its performance and usage scope.

Key Data Assumptions

Assumption Description Impact
Document Authority Internal RBC policies are considered more authoritative than external sources Ensures organizational standards are prioritized
Content Correctness Documents in designated storage locations are assumed to be correct and authoritative Enables efficient processing without additional validation steps
Source Completeness The knowledge base is assumed to contain all relevant policy documentation Critical for providing comprehensive responses
Document Structure Higher-level document sections are assumed to contain more important policy statements Influences retrieval and ranking algorithms
Query Context User intent is assumed to remain consistent within a conversation Enables effective follow-up handling

Data Limitations

Limitation Description Impact on Usage
Content Currency Lag between document updates and database refresh Responses may not reflect very recent policy changes
Visual Content Processing Limited ability to fully capture complex tables, charts, and financial diagrams Some visual information may be simplified or summarized
Information Boundaries System can only access information in its knowledge base Cannot leverage information beyond processed documents
Calculation Handling Unable to execute or validate accounting calculations in source materials Cannot verify calculation results or run new scenarios
Language Support Optimized for English content with limited multilingual capabilities May not fully process non-English segments in documents

Future Improvements

The IRIS system is designed for continuous improvement through several planned enhancements:

  1. Documentation Updates
  2. Regular refresh cycles to incorporate policy changes

  3. Expansion of the knowledge base to cover additional finance domains

  4. Processing Enhancements

  5. Improvements to visual content processing for complex financial diagrams
  6. Better preservation of document relationships and cross-references

The system's modular design allows for component-level improvements without requiring complete system redesign.
