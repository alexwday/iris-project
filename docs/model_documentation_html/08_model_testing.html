8. Model Testing

Model Name: IRIS (Intelligent Research and Information System) Model ID: IRIS-001

This section documents the testing methodology and results used to validate the IRIS system. The testing focused on evaluating the system's ability to retrieve relevant information from knowledge sources and generate appropriate responses across a range of finance and accounting policy queries.

Note: Supporting test artifacts are available in the following SharePoint folders: - Test Questions: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/TestQuestions/ (contains APG and non-APG test query sets) - APG Feedback: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/APGFeedback/ (contains detailed feedback from APG reviewers) - Quantitative Results: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/QuantitativeResults/ (contains metrics and analysis for non-APG databases) - APG Signoff: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/APGSignoff/ (contains final signoff documentation from APG team)

8.1 Testing Approach

The IRIS testing strategy centered on an iterative, database-by-database development and testing approach, with a focus on ensuring that the agent-based architecture and knowledge retrieval mechanisms functioned correctly to produce accurate, policy-compliant responses.

8.1.1 Query Dataset Development

Two distinct query sets were developed for comprehensive testing:

  1. APG-Focused Queries: Approximately 50 example queries provided by the Accounting Policy Group (APG), specifically targeting accounting policy databases.

  2. CFO-Focused Queries: Approximately 50 additional queries curated by the internal team, designed to test broader CFO group databases.

These queries were deliberately created to cover common inquiry types and critical finance and accounting areas across all integrated knowledge sources.

Note: The complete set of test queries used for system validation is available in the SharePoint folder: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/TestQuestions/

8.1.2 Iterative Testing and Development Process

Testing and development were conducted through an incremental, database-by-database approach:

  1. Method Development Phase:
  2. Initial retrieval method was developed for a single database
  3. Test outputs were generated and sent to the APG team for review
  4. Feedback was collected and analyzed
  5. Enhancements were implemented based on feedback

  6. Process was repeated until performance was satisfactory for that database

  7. Method Expansion Phase:

  8. When starting integration with a new database, the existing method was tested first
  9. If performance was insufficient, a new method was developed
  10. This led to the development of three distinct retrieval methods and five data processing pipelines

  11. Each new method underwent the same iterative feedback and enhancement process

  12. Comprehensive Testing Phase:

  13. Once all databases and methods were implemented, a final round of testing was conducted
  14. APG databases received final signoff from the APG team
  15. Non-APG databases were evaluated with detailed scoring metrics
  16. Results were aggregated into a comprehensive evaluation report

This development approach ensured that each database and retrieval method was optimized for the specific document types it contained. Testing was conducted using the Dataiku implementation, which has been made available to business users for providing feedback.

8.1.3 Testing Methodology

The testing process involved structured evaluation across multiple dimensions:

  1. Question Submission: Test questions were submitted to the model through the Dataiku interface

  2. Performance Recording: For each question, evaluators recorded:

  3. Database selection accuracy: Did the system select the appropriate database(s)?
  4. Document selection accuracy: Did the system retrieve the relevant documents?
  5. Response quality: Overall score of the generated response

  6. Paragraph-level feedback: Detailed comments on each section of the response

  7. Documentation: All results were recorded in Excel templates for consistent evaluation

  8. Analysis: Results were aggregated to calculate performance metrics and identify improvement areas

  9. Negative Testing: Additional tests specifically probed system boundaries and restrictions to ensure appropriate guardrails were functioning

8.2 Testing Results

8.2.1 Key Performance Metrics

The final comprehensive testing phase yielded specific performance metrics for the non-APG databases:

  1. Overall Performance Score: 89.6% based on reviewer evaluations

  2. Database Selection Accuracy: 99.4% accuracy in selecting the appropriate knowledge source(s)

  3. Document Selection Accuracy: 97.7% accuracy in retrieving relevant documents from selected databases

  4. Answer Accuracy: 94.2% (calculated based on reviewer comments and evaluation notes)

Note: Complete quantitative test results and detailed metrics are available in the SharePoint folder: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/QuantitativeResults/

For APG databases, the evaluation process involved direct feedback and signoff rather than numerical scoring. The APG team provided expected answers for each test question and evaluated whether the system outputs met these expectations. Final signoff was received for all 50 APG test questions, confirming satisfactory performance.

Note: Final APG signoff documentation is available in the SharePoint folder: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/APGSignoff/

Given the shared retrieval methods between APG and non-APG databases, and the positive feedback from both evaluation processes, the system demonstrates consistently strong performance across all knowledge sources.

8.2.2 Identified Issues and Resolutions

Through the iterative testing process, several issues were identified and addressed. The following represents key issues from actual business feedback:

Note: Detailed feedback from APG reviewers, including issue reports and suggested improvements, is available in the SharePoint folder: https://rbcds.sharepoint.com/sites/IRISProject/Shared Documents/TestArtifacts/APGFeedback/

  1. Unsolicited IFRS vs. GAAP Comparisons:
  2. Issue: The system included IFRS vs. GAAP comparisons even when not requested, making responses unnecessarily long.

  3. Resolution: Enhanced prompt instructions for the CAPM subagent to focus only on the standard relevant to the query (defaulting to IFRS if none specified) and actively filter out information about other standards unless explicitly requested.

  4. Incomplete Answers Due to Sequential Database Processing:

  5. Issue: Responses sometimes contained information only from one database (e.g., CAPM) when relevant information also existed in others (e.g., APG Wiki).

  6. Resolution: Implemented parallel database querying and updated the Summarizer agent to synthesize findings from all sources into a comprehensive response.

  7. Overly Verbose Response Format:

  8. Issue: Responses included excessive internal processing details like "Thought", "Clarify", "Researching", making outputs long and difficult to follow.

  9. Resolution: Eliminated internal "thinking" steps from display, streamlined clarification and research status updates, and configured the Summarizer to generate only the final, synthesized report.

  10. Incorrect Handling of Finance-Related Queries:

  11. Issue: Basic finance concept definitions were sometimes answered directly without database research, risking responses based on the model's training data.

  12. Resolution: Updated the Router agent to explicitly route all finance-related queries (including basic definitions) to the research path, and enhanced the Direct Response agent to refuse answering finance queries without prior research results.

  13. Missing Critical Information:

  14. Issue: Specific, critical pieces of information (like conditions or criteria) were sometimes missing from responses.

  15. Resolution: Enhanced prompts for subagents to accurately extract specific conditions or tests, and for the Summarizer to preserve these details in the final synthesis.

  16. Unnecessary Detail in Responses:

  17. Issue: Even when asking about specific aspects (e.g., classification of financial assets), responses included details on unrelated aspects (e.g., measurement, impairment).

  18. Resolution: Implemented adaptive synthesis logic to match the scope of the response to the specific user request, providing concise answers for targeted questions.

  19. Inconsistent Spacing/Formatting:

  20. Issue: Response formatting showed inconsistencies in spacing, indentation, and Markdown usage.

  21. Resolution: Enhanced formatting instructions for the Summarizer agent with explicit guidelines for handling headings, lists, paragraph spacing, and proper Markdown structure.

  22. Incorrect Labeling of Source Authority:

  23. Issue: External firm guidance (EY, KPMG, PwC) was incorrectly labeled as "authoritative" when only standards bodies like IASB are authoritative.
  24. Resolution: Updated source descriptions to clearly label external firm guidance as "External Supplementary" and IASB as "External Authoritative," ensuring correct source hierarchy understanding.

8.2.3 User Interface Issues Addressed

Several issues related to the user interface were also identified and addressed:

  1. Inability to Scroll During Response Streaming:
  2. Issue: Users couldn't scroll up to view previous messages during response generation.

  3. Resolution: Modified the UI code to allow scrolling during streaming while maintaining auto-scroll after completion.

  4. Non-functional Feedback Controls:

  5. Issue: Thumbs up/down icons didn't function in the test environment.

  6. Resolution: Clarified that these features are planned for the production implementation.

  7. Graphical Content Display:

  8. Issue: Users requested the ability to see actual graphical cheat sheets rather than text descriptions.
  9. Resolution: Implemented multi-pass vision preprocessing to extract detailed content from graphical elements while acknowledging the current text-only display limitation.

8.3 Implementation of Feedback

The feedback collection and implementation process was systematic and thorough:

  1. Feedback Collection:
  2. Detailed comments were collected from APG reviewers for each test query
  3. Excel templates documented performance across multiple dimensions

  4. Issues were categorized by frequency and impact

  5. Issue Prioritization:

  6. High-impact issues (affecting response accuracy) were addressed first
  7. Widespread issues affecting multiple queries were prioritized

  8. UI/UX enhancements were scheduled according to their impact on usability

  9. Implementation Approach:

  10. System components were refined through targeted prompt engineering
  11. Core architectural changes (e.g., parallel database querying) were implemented

  12. UI enhancements were developed in coordination with front-end teams

  13. Verification:

  14. Each implemented fix was verified through targeted testing
  15. Previously problematic queries were re-tested to confirm improvements
  16. Full test suites were re-run to ensure no regression

This systematic approach to feedback implementation ensured continuous improvement of the system throughout the development cycle.

8.4 Model Components Validation

While IRIS doesn't implement custom model training, it leverages pre-trained models in specific ways. The testing validated the effectiveness of these model components:

8.4.1 Pre-trained Models Performance

  1. GPT-4o and GPT-4o-mini: These models serve as the primary reasoning engines within the agent architecture. Testing confirmed that:
  2. They effectively interpret user queries and generate appropriate research statements
  3. They can accurately select relevant documents from catalog descriptions
  4. They generate coherent, well-structured responses from retrieved information

  5. They maintain appropriate limitations and disclaimers in responses

  6. Embedding Model (text-embedding-3-large): This model generates vector representations for semantic search. Testing verified:

  7. High-quality semantic similarity matching between queries and documents
  8. Effective ranking of relevant documents

  9. Appropriate balance between precision and recall in search results

  10. Qwen2 Vision Model: This model processes infographics and visual documents. Testing confirmed:

  11. Accurate extraction of text from visual elements
  12. Proper interpretation of charts, tables, and diagrams

  13. Effective conversion of visual information to structured text format

  14. Cohere command-north-large: This on-premises deployed model is used for database refresh pipelines. Validation confirmed:

  15. Effective processing of external IFRS guidance documents
  16. Proper metadata generation and summarization
  17. Appropriate data privacy preservation for external content

The performance of these pre-trained components was deemed satisfactory for production use based on the query testing results, with no formal pre-testing required due to reliance on established benchmarking statistics that demonstrate sufficient capabilities.

8.4.2 Retrieval Method Validation

Each retrieval method was validated for its specific use case through the iterative testing process described above. This database-by-database approach ensured that the appropriate method was selected for each content type:

  1. Catalog Search - Small: Demonstrated effectiveness for standard documents with simple structure.

  2. Catalog Search - Large: Proven appropriate for larger documents with distinct sections, maintaining document context while focusing on relevant sections.

  3. Catalog Search - Excel: Successfully handled structured data from Excel sources, maintaining tabular format and relationships.

  4. Catalog Search - Vision: Verified ability to extract and structure information from visual documents, making infographics accessible to the query pipeline.

  5. Semantic Search - Large: Confirmed effectiveness for very large reference documents, retrieving relevant passages while maintaining appropriate context.

These methods were selected based on document characteristics and evolved through the iterative testing process, with each method optimized for specific document types and structures.

8.4.3 Guardrail Testing

Negative testing was conducted to verify the system's ability to recognize and appropriately respond to out-of-scope queries. These tests confirmed that:

  1. The system correctly identifies queries outside its knowledge domain
  2. Appropriate disclaimers are provided when queries cannot be answered
  3. The system maintains proper boundaries regarding financial advice and regulatory guidance
  4. Messages consistently include required disclaimer statements

This testing validated that the safety guardrails implemented in the system function as intended, ensuring appropriate use within defined boundaries.

8.5 Current Implementation and Future Integration

The IRIS system has been implemented in Dataiku as a Dash web application for initial testing and feedback. This implementation has been made available to business users for evaluation and has undergone multiple rounds of refinement based on their feedback.

The current status of the system includes:

  1. Functional Implementation: The complete IRIS functionality is operational in the Dataiku environment, with all agent components functioning as designed.

  2. Database Connectivity: All database connections have been established and validated, with proper access controls implemented.

  3. User Feedback Collection: Business users have provided feedback on the system's performance and response quality, which has been incorporated into ongoing refinements.

  4. Maven Integration Planning: The IRIS code is being prepared for integration into the Maven UI, with plans to have a working demonstration available in the Maven development environment by June 2025.

The Maven integration will maintain the same core functionality with no code changes to the underlying model. The integration will primarily focus on adapting the API interface to work within the Maven ecosystem while using the same PostgreSQL database for knowledge retrieval.

8.6 Testing Limitations

It is important to acknowledge several limitations in the testing approach:

  1. No Blind Testing: Due to resource constraints, formal blind testing with independent evaluators was not conducted. Testing relied on the same teams involved in development.

  2. Limited Statistical Validation: Given the nature of the system as a RAG implementation rather than a custom-trained model, extensive statistical validation was not performed.

  3. No Formal Benchmark Comparison: Alternative RAG architectures or methods were not explicitly tested as comparisons, as method selection was based on prior experience and project requirements.

  4. Limited Load Testing: While basic functionality was confirmed, extensive load or stress testing to identify performance boundaries was not conducted.

  5. Subject Matter Expert Availability: Testing relied on available subject matter experts rather than a formal, diverse panel of evaluators.

  6. Testing Environment Limitations: Testing has been conducted primarily in the Dataiku environment, with full Maven integration testing pending.

These limitations are considered acceptable given the nature of the project and its intended use as an internal tool with human oversight.

8.7 Testing Conclusions

The testing conducted for the IRIS system provides reasonable confidence in its ability to serve its intended purpose:

  1. Core Functionality: The system effectively retrieves relevant information from finance and accounting knowledge sources and generates appropriate, well-structured responses, with quantitative metrics supporting this conclusion (99.4% database selection, 97.7% document selection, 94.2% answer accuracy).

  2. Knowledge Boundaries: The system appropriately identifies when information is outside its knowledge base and provides appropriate disclaimers, as confirmed through negative testing.

  3. Response Quality: With iterative improvements based on testing feedback, the system's response quality reached a level deemed acceptable for production use, with formal signoff from the APG team and an overall performance score of 89.6%.

  4. Document Integration: Through the database refresh process, the system can incorporate new documents, enabling it to remain current as policies evolve.

Based on the testing results, the IRIS system is considered suitable for deployment as a finance and accounting policy guidance tool, with the understanding that human oversight remains essential for verifying responses on critical matters. The feedback collection mechanism and ongoing monitoring will support continuous improvement as the system is used in practice.
