7. Model Implementation

Model Name: IRIS (Intelligent Research and Information System) Model ID: IRIS-001

7.1 Software / Coding

IRIS employs a modular architecture organized around specialized agents and knowledge sources. The system implementation consists of the following main components:

7.1.1 System Architecture

The IRIS system operates through a multi-tier architecture:

  • Maven UI: The user-facing application that provides the interface for interacting with IRIS
  • IRIS API: Core model functionality deployed as an API service
  • Database Services: PostgreSQL database with pgvector extension for document and vector storage
  • LLM Gateway: Integration with RBC's Lumina portal for accessing large language models

The system functions as follows:

  1. Maven Interface: Users interact with the Maven UI, which manages:
  2. User authentication and access control through Active Directory groups
  3. Authorization for specific database access based on user role
  4. Conversation history and session management

  5. User interface presentation and streaming of responses

  6. IRIS Model API: The IRIS model code functions as an API and:

  7. Receives conversation context and authorized database access from Maven
  8. Processes queries through the agent framework
  9. Returns streaming responses back to Maven

  10. Logs process monitoring data for performance tracking

  11. Database Management:

  12. Separate PostgreSQL tables for knowledge retrieval and process monitoring

  13. Database refresh occurs on a set schedule (quarterly or yearly, depending on the database)

  14. LLM Integration:

  15. IRIS connects to language models through RBC's Lumina portal

Currently, the IRIS code has been implemented and deployed in Dataiku as a Dash web application demo. This same code is being integrated into the Maven UI for the production implementation. Both implementations interact with the same PostgreSQL database, with no changes being made during the transition from Dataiku to Maven.

7.1.2 Agent Framework

The agent system is implemented as a collection of Python modules, each responsible for specific aspects of query processing as described in Section 6.1:

  • Router Agent: Implemented in /iris/src/agents/agent_router/router.py, determines the optimal processing path for each query by analyzing query intent and required knowledge sources.

  • Clarifier Agent: Implemented in /iris/src/agents/agent_clarifier/clarifier.py, ensures queries contain sufficient context before research begins by identifying and requesting missing information.

  • Planner Agent: Implemented in /iris/src/agents/agent_planner/planner.py, creates research plans by selecting appropriate knowledge sources and setting search parameters.

  • Database Subagents: Implemented in /iris/src/agents/database_subagents/, specialized modules for retrieving information from specific knowledge sources:

  • Internal sources (CAPM, Cheatsheets, Compliance, etc.)

  • External sources (EY, IASB, KPMG, PwC)

  • Summarizer Agent: Implemented in /iris/src/agents/agent_summarizer/summarizer.py, synthesizes findings into coherent, properly cited responses.

  • Direct Response Agent: Implemented in /iris/src/agents/agent_direct_response/response_from_conversation.py, generates responses based solely on conversation history without database access.

Data flows between agents through structured JSON messages containing the query context, research parameters, retrieved information, and synthesized responses. Each agent maintains its own state during processing and passes relevant information to downstream agents.

7.1.3 Knowledge Store Implementation

The IRIS knowledge store is implemented as a PostgreSQL database with the following structure:

Core Database Tables

  1. apg_catalog: Document metadata repository
  2. Document identification (source, type, name)
  3. Document description and usage information

  4. File metadata (creation date, modification date, size, path)

  5. apg_content: Document content storage

  6. References to documents in apg_catalog
  7. Section-based content organization

  8. Section summaries and full content text

  9. iris_textbook_database: Vector-enabled document chunk storage

  10. Document and section structural positioning (as detailed in Section 5)
  11. Chapter-level metadata with tags and summaries
  12. Section-level pagination and importance scoring
  13. Content text and 2000-dimension vector embeddings

  14. Full-text search vector for text-based queries

  15. process_monitor_logs: Performance tracking system

  16. Detailed logging of each model invocation
  17. Timing and token usage metrics for each processing stage
  18. LLM call details stored as structured JSON

Database Connectivity

The system connects to the database through a standardized configuration layer in /iris/src/initial_setup/db_config.py, which: * Provides connection parameters for both local development and RBC environments * Handles connection management and error recovery * Verifies the existence of required tables

Database Processing Methods

The IRIS system employs five distinct approaches for knowledge retrieval (as detailed in Section 6.2):

  1. Catalog Search - Small: Used for standard documents with simple structure
  2. Two-stage selection with catalog prioritization
  3. Document selection through LLM evaluation of metadata
  4. Full section retrieval for selected documents

  5. Used for databases like internal_par and internal_process_and_controls

  6. Catalog Search - Large: Used for large documents with hierarchical structure

  7. Three-stage hierarchical selection using LLM judgment
  8. Section summary evaluation for targeted content retrieval

  9. Used for databases like internal_capm and internal_global_finance_standards

  10. Catalog Search - Excel: Used for tabular data sources

  11. Table preprocessing with row-level document conversion
  12. Table format preservation in Markdown

  13. Used for databases like internal_wiki and internal_management_reporting

  14. Catalog Search - Vision: Used for infographics and visual content

  15. Image-to-text conversion using multi-pass vision transformer
  16. Multi-pass extraction of text, tables, and diagrams

  17. Used for visual content in internal_cheatsheets

  18. Semantic Search - Large: Used for extensive reference materials

  19. Vector-based similarity search with token-aware chunking
  20. Sophisticated reranking based on importance scores and vector similarity
  21. Section expansion and sequence gap filling
  22. Used for external sources like external_ey, external_iasb, external_kpmg, and external_pwc

The database subagents implement these different approaches based on the specific requirements of each knowledge source, with a central database router (database_router.py) directing queries to the appropriate subagent.

7.1.4 Model Integration

IRIS integrates with large language models through the RBC Lumina portal:

  • LLM Connector: Implemented in /iris/src/llm_connectors/rbc_openai.py, provides a consistent interface for agent-LLM communication.
  • Model Settings: Configuration parameters defined in /iris/src/llm_connectors/rbc_openai_settings.py.

The system employs: * GPT-4o: For complex reasoning tasks like research synthesis, clarification, and content generation * GPT-4o-mini: For decision tasks like routing, database selection, and document filtering * text-embedding-3-large: For generating vector embeddings used in semantic search * Qwen2: For vision processing of infographics and other image content

Each model is accessed with customized prompt engineering to ensure consistent outputs across the agent architecture.

7.1.5 Process Monitoring

The IRIS system includes comprehensive process monitoring capabilities:

  • Performance Tracking: Every model call is logged with detailed performance metrics
  • Process Stages: All pipeline stages are tracked with timing and token usage information
  • Error Logging: Structured logging of any issues or exceptions encountered
  • Usage Analytics: Aggregated statistics on system usage patterns

The monitoring framework is implemented in /iris/src/initial_setup/process_monitor.py and records detailed information about each model invocation in the process_monitor_logs table. This enables:

  1. Real-time Performance Monitoring: Active tracking of system responsiveness
  2. Cost Optimization: Analysis of token usage patterns to identify optimization opportunities
  3. Error Detection: Early identification of potential issues in the processing pipeline
  4. Usage Pattern Analysis: Understanding of common query types and knowledge source utilization

The monitoring system outputs can be analyzed using the Jupyter notebooks in the /notebooks/ directory, particularly process_monitor_analysis.ipynb, which provides visualization and statistical analysis of system performance metrics.

7.1.7 Development and Deployment

The IRIS code is currently running as a Python library in two environments:

  • Dataiku: Implemented as a Dash web application for demonstration and business user feedback. This implementation has been made available to business users who have provided feedback that has been incorporated into ongoing development.
  • Local Development: Used for ongoing development and testing

The code is being provided to the Maven team for integration into their UI, with plans to have the functional demonstration available in the Maven development environment by June 2025. The integration will maintain the same core functionality with no changes to the underlying model code, focusing primarily on adapting the API interface to work within the Maven ecosystem. The requirements and setup are all packaged within the model code to facilitate deployment.

7.1.8 Code Quality Assurance

The IRIS development team employs several approaches to ensure code quality:

  • Code Formatting: Black is used to enforce consistent code formatting with an 88 character line limit
  • Linting: Pylint is used to identify potential code issues and ensure adherence to coding standards
  • Testing: The code is tested in Dataiku running as a Python library and locally for development work
  • Deployment Validation: The code will be retested once hosted in OpenShift to confirm the same working behavior

These practices help identify and resolve potential issues, ensuring that the production system remains stable and performant.

7.1.9 Implementation Alignment with Model Design

The implementation of IRIS directly realizes the model design and approach described in the previous sections. Key points of alignment include:

  1. Agent-based Architecture: The implementation follows the modular agent framework described in Section 4.1, with specialized agents for different processing tasks.

  2. Hybrid RAG Approach: The system implements the hybrid retrieval-augmented generation approach detailed in Section 4.1, using different processing pipelines based on document types.

  3. Retrieval Methods: The five distinct retrieval methods described in Section 6.2 are directly implemented in the database subagents, with specific optimizations for each knowledge source.

  4. Model Parameter Configuration: The implementation uses the model parameters specified in Section 6.4.1, with temperature settings and other configurations aligned with the documented approach.

  5. Token-Aware Processing: The system implements the token-aware chunking algorithm detailed in Section 6.5.2, ensuring optimal information density while maintaining semantic coherence.

  6. Monitoring Framework: The process monitoring system implements the metrics collection and storage approach described in Section 6.6, providing comprehensive performance tracking.

This direct alignment between design and implementation ensures that the theoretical approach is properly realized in the system.
