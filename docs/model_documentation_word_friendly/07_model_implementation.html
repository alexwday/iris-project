Model Implementation

Model Name: IRIS (Intelligent Research and Information System)
Model ID: IRIS-001

Software / Coding

IRIS employs a modular architecture organized around specialized agents and knowledge sources. The implementation follows a multi-tier approach with clearly defined components and interfaces.

System Architecture

IRIS operates through a multi-tier architecture comprising four main components: the Maven UI (user-facing interface), IRIS API (core model functionality), Database Services (PostgreSQL with pgvector extension), and LLM Gateway (integration with RBC's Lumina portal). The system workflow begins with users interacting through the Maven Interface, which handles authentication via Active Directory groups, database access authorization based on user roles, conversation history management, and response streaming. The IRIS Model API processes queries through the agent framework and returns streaming responses while logging performance metrics. Database Management includes dedicated PostgreSQL tables for knowledge retrieval and process monitoring, with scheduled refreshes (quarterly or yearly depending on content type). LLM Integration occurs through RBC's Lumina portal, providing access to the required language models.

The development and deployment progress has followed a structured path. IRIS was first implemented locally as a Python library, then deployed to Dataiku as a Dash web application for business user feedback and testing. The same code is now being integrated into the Maven UI for production implementation, with both environments interacting with the same PostgreSQL database. The transition from Dataiku to Maven involves no changes to the underlying model code, focusing only on adapting the API interface to work within the Maven ecosystem.

Agent Framework Implementation

The agent system is implemented as a collection of Python modules that process user queries through a structured pipeline. The Router Agent (/iris/src/agents/agent_router/router.py) analyzes query intent to determine the optimal processing path. For queries requiring research, the Clarifier Agent (/iris/src/agents/agent_clarifier/clarifier.py) ensures sufficient context is available before proceeding. The Planner Agent (/iris/src/agents/agent_planner/planner.py) then creates a research strategy by selecting appropriate knowledge sources. Specialized Database Subagents (/iris/src/agents/database_subagents/) retrieve information from specific sources, and the Summarizer Agent (/iris/src/agents/agent_summarizer/summarizer.py) synthesizes findings into coherent responses. For straightforward queries, the Direct Response Agent (/iris/src/agents/agent_direct_response/response_from_conversation.py) generates answers using only conversation history. Data flows between agents through structured JSON messages containing query context, research parameters, retrieved information, and synthesized responses.

Knowledge Store Architecture

The IRIS knowledge store is implemented as a PostgreSQL database with four core tables. The apg_catalog table serves as a document metadata repository, containing identification details, descriptions, and file metadata. The apg_content table stores document content with references to apg_catalog, organizing content by sections with both summaries and full text. The iris_textbook_database provides vector-enabled document chunk storage with structural positioning, metadata, content text, and 2000-dimension vector embeddings. The process_monitor_logs table tracks performance metrics, recording timing and token usage for each processing stage.

Database connectivity is managed through a standardized configuration layer (/iris/src/initial_setup/db_config.py) that handles connection parameters, management, error recovery, and table verification across environments. Information retrieval operates through three primary methodologies: Catalog Search - Small for standard documents, Catalog Search - Large for documents with hierarchical structure, and Semantic Search - Large for extensive reference materials. These are implemented through database subagents directed by a central router (database_router.py) that assigns queries to the appropriate processing approach.

Model Integration and Monitoring

IRIS integrates with large language models through RBC's Lumina portal via an LLM Connector (/iris/src/llm_connectors/rbc_openai.py) that provides a consistent interface for agent-LLM communication. The system employs multiple models optimized for different tasks: GPT-4o for complex reasoning and content generation, GPT-4o-mini for routing and selection decisions, text-embedding-3-large for vector representations in semantic search, and Qwen2 for vision processing. Each model is accessed with customized prompts designed for consistent outputs across the agent architecture.

Comprehensive process monitoring is implemented through a framework (/iris/src/initial_setup/process_monitor.py) that records detailed metrics for each model invocation in the process_monitor_logs table. This system tracks performance at each processing stage, collects token usage statistics, logs errors, and aggregates usage patterns. These metrics enable real-time performance monitoring, cost optimization, early error detection, and usage pattern analysis. The monitoring outputs can be analyzed using Jupyter notebooks in the /notebooks/ directory, particularly process_monitor_analysis.ipynb, which provides statistical analysis of system performance.

Quality Assurance

The IRIS development team employs several approaches to ensure code quality throughout the implementation process. Code formatting is enforced using Black with an 88-character line limit to maintain consistent style. Linting with Pylint identifies potential code issues and ensures adherence to coding standards. Testing occurs in both Dataiku and local development environments to validate functionality. Deployment validation will include retesting once the code is hosted in OpenShift to confirm consistent behavior across environments. These practices help identify and resolve potential issues before they impact the production system, ensuring stability and reliability for end users.

Implementation Testing

IRIS implementation testing follows a structured path across multiple environments. The system was first built and tested locally in Python, then deployed to Dataiku as a Python + Dash web application for business feedback and validation. This Dataiku implementation has been made available to business users who have provided valuable input on functionality and response quality, with their feedback incorporated into ongoing development.

The implementation is now transitioning to Maven, where it will operate on the same PostgreSQL database used in the Dataiku testing phase. The deployment path includes several validation stages: development environment testing with Digital Ecosystem & AI team oversight, UAT environment testing involving end users, and finally, production deployment with formal PIV (post-implementation verification) testing.

For ongoing changes and improvements, a structured change control process has been established. First, fixes and enhancements are developed and tested locally in Python. When validated, these changes are provided to the Maven team for implementation in the development environment, where the Digital Ecosystem & AI team verifies they're working as expected. The Maven team then pushes these changes to the UAT SAI environment for further testing before creating a change request to move the approved code to production.

Final comprehensive implementation testing will be performed in June when the system is fully integrated into the Maven production environment. This testing will validate that the system behaves as expected in its final deployment context and meets all business requirements identified during the development and feedback cycles.

Change Controls and Security

IRIS implements a multi-layered approach to change control and security to maintain system integrity. All code changes follow a structured review and deployment process that begins with local development and testing, followed by implementation in development, UAT, and production environments, each requiring explicit verification before proceeding to the next stage. Code repositories are protected with access controls limiting modification rights to authorized development team members, with branch protection rules enforcing code review requirements before changes can be merged.

System access is managed through Maven's authentication and authorization framework, with Active Directory integration determining user access rights. Permissions are role-based, controlling both system access and visibility of specific knowledge sources based on user responsibilities. The LLM connection is secured through RBC's Lumina portal, which provides enterprise-grade security for model access including encryption of all communications, API key management, and usage monitoring.

Database security includes encrypted connections, role-based access controls, and audit logging of all access attempts. All user queries and system responses are logged with user identification for accountability and audit purposes, but sensitive information is automatically redacted from these logs using pattern matching to ensure compliance with data protection requirements. Regular security reviews and vulnerability assessments are conducted as part of RBC's standard security protocols, ensuring ongoing protection as the system evolves.
